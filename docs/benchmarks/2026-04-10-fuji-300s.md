This was a real cold-start benchmark against the shared Fuji production surface. The runs were sequential on the same host, but not from one uninterrupted wrapper invocation: the `avalanche-rs` run completed first, then AvalancheGo was rerun after fixing an invalid `--staking-enabled` launcher flag in the harness. Both runs started from empty local state.

## What This Run Actually Showed

- `avalanche-rs` stayed materially smaller in memory than AvalancheGo during the same 5-minute cold-start window.
- AvalancheGo brought up its HTTP surface quickly, had 42 peers by the end of the run, but did not bootstrap P-Chain inside 5 minutes and still reported unhealthy state.
- `avalanche-rs` answered parts of the C-Chain public RPC slice within 5 minutes, but it also exposed real parity bugs during the benchmark:
  - `platform.getHeight` returned an impossible value (`8725724278057432`) even though the logs showed a Fuji tip around height `273022`.
  - `info.peers` did not yield a usable response in the same window.
  - `/ext/health` never produced a usable benchmark response in the same window.
  - C-Chain remained at block `0x0`.

## Scope Notes

- This benchmark covers the shared production surface that both implementations expose in a 5-minute cold-start window: process start, peer connectivity, sync progress, resource usage, health, and a common RPC slice.
- It does not prove parity for every non-overlapping API family or every long-horizon operational behavior.
- The benchmark is still useful because it exercises both nodes against real Fuji networking and records the current failure modes instead of hiding them.
